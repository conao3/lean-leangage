# AGENTS.md

leanharbor: the contract of a kernel proved in Lean 4, and the shells that run the code
[leanfran](https://github.com/conao3/lean-leanfran) generates from it.

## Layout

- `lean/`: Lake package `leanharbor`, Lean 4.35.0, core only (no Mathlib). `Leanharbor/Kernel.lean`
  is the contract, `Leanharbor/Obligation.lean` the statements every kernel's theorems must state
  exactly, `Leanharbor/Sql.lean` the SQL compiler that is generated,
  `Leanharbor/Sql/Proofs.lean` its specifications and theorems, `Leanharbor/Sql/Model.lean` a
  model of PostgreSQL and what a statement means to a tenant, `Leanharbor/Sql/Sound.lean` the
  theorems that the compiled statements do that under the model, `Leanharbor/Sql/Isolation.lean`
  tenant isolation, and `Leanharbor/Store.lean` the class `Row`, the storage of a kernel
  (`Storage`) and the theorems proved once for every storage. `Leanharbor/Token.lean` is the
  token format that is generated and `Leanharbor/Token/Proofs.lean` its theorems.
  `Leanharbor/Json.lean` is the JSON writer that is generated and `Leanharbor/Json/Proofs.lean`
  its specification (a printer over JSON values, a string lexer) and theorems.
  `Calculator/Kernel.lean` holds what is generated, `Calculator/Proofs.lean` the specifications
  and theorems; `Calculator/Store.lean` (generated) the calculator's table and row functions,
  `Calculator/Store/Proofs.lean` the calculator's `Storage` and its theorems.
  `Leanharbor/Authz.lean` is the authorization guard and `Leanharbor/AuthzProofs.lean` its
  theorems. `Notes/` is the example with a policy, in the layout of `Calculator/`.
  `CalculatorOracle.lean`, `NotesOracle.lean`, `SqlOracle.lean`, `TokenOracle.lean` and
  `JsonOracle.lean` are the native programs the differential tests compare against.
- `audit/`: a separate Lake package with leanassay (`Audit/Calculator.lean`, `Audit/Sql.lean`,
  `Audit/Store.lean`, `Audit/Token.lean`, `Audit/Json.lean`, `Audit/Authz.lean`, `Audit/Notes*.lean`), the axiom
  check (`Audit/Axioms.lean`) and the obligation check `#obligations` (`Audit/Obligations.lean`,
  run on the calculator in `Audit/Calculator.lean` and on the notes in
  `Audit/NotesObligations.lean`). Each file in `audit/fail/` must fail to build with the error on
  its `-- expect:` line; `make check` builds them with `lake -d audit env lean`. A file is built
  only when it is in `roots` of `audit/lakefile.toml` or imported by `Audit.lean`. `#assay`
  derives instances named after the short names of the types it samples, so two audit files whose
  types share a short name (`Snapshot`) are separate roots and do not import each other.
- `rust/`: Cargo workspace, edition 2024. `leanharbor` is the shell, `leanharbor-pg` the engine
  that stores the snapshots in PostgreSQL, `calculator` and `notes` the examples.
- `python/`: uv project. `leanharbor` is the shell, `leanharbor_calculator` and `leanharbor_notes`
  the examples.
- `go/`: Go module `github.com/conao3/lean-leanharbor/go`. `leanharbor` is the shell,
  `calculator` and `notes` the examples, with the calculator's server and benchmark under
  `calculator/cmd/`.
- Each shell holds the SQL compiler generated from `Leanharbor.Sql`: `rust/leanharbor/src/generated/`
  (`leanharbor::sql`), `python/src/leanharbor/sql.py` and `go/leanharbor/sql/`. The calculator's
  table from `Calculator.Store` is `rust/calculator/src/generated/calculator_store.rs`,
  `python/src/leanharbor_calculator/store.py` and `go/calculator/store/`. Each shell holds
  the token format generated from `Leanharbor.Token` (`leanharbor::token_format`,
  `python/src/leanharbor/token_format.py`, `go/leanharbor/token/`), and its `token` module calls
  `encodePayload`, `join` and `parse` and computes and compares the HMAC and checks the expiry.
  Each shell holds the JSON writer generated from `Leanharbor.Json` (`leanharbor::json_format`,
  `python/src/leanharbor/json_format.py`, `go/leanharbor/jsonformat/`) and writes its own
  `{"error": ...}` bodies with it; the calculator's replies and refusals are the bytes of the
  generated `encodeReply` and `encodeError`.
- The Rust calculator's table is generated by `leanfran module generate` with
  `--type-path Calculator.Kernel=crate::generated::calculator_kernel Leanharbor.Sql=::leanharbor::sql`,
  so that `load` and `writes` take and return the kernel's types and those of `leanharbor::sql`;
  `rust/calculator/src/lib.rs` declares it as the module `store`. A kernel stored in PostgreSQL
  implements `leanharbor::Storage` by delegating to such a module.

## Lean and the host languages

- Lean owns the kernel: types, `transition`, `apply`, and every decision about a command.
  Definitions that are generated go in a module without proofs (`Calculator.Kernel`); theorems
  and specifications go in a module beside it (`Calculator.Proofs`).
- The shells own input and output: HTTP, tokens, JSON, the engine. They call generated
  functions and make no decision about a command themselves. The PostgreSQL engine sends only the
  text of the generated `render` for a kernel's tables, with the values as parameters; its own
  statements are the constants of `rust/leanharbor-pg/src/lib.rs` (transaction control, advisory
  locks, `leanharbor_idempotency`) and the role statements of `lockdown`.
- The contract uses `Except` for refusals. The engines keep each tenant's snapshot as a Lean
  value with one owner (`leanfran::Owned` in Rust, lent as a `Local` by `Kernel::lend`;
  `leanfran.Local` in Python; `leanfran.Value` in Go) and call the generated functions that take
  one (`kernel::local::apply` in Rust, `kernel.apply.local` in Python, `kernel.Handle.Apply` in Go).
  `apply` must receive the only reference to the snapshot (a move in Rust, `take()` in Python,
  `Take()` in Go), and no `Local` may leave the closure of `lend`, or Lean copies instead of
  updating in place. `rust/calculator/tests/in_place.rs` and `go/calculator/in_place_test.go`
  check it.
- Generated files (`rust/*/src/generated/`, `python/src/leanharbor_*/kernel.py`,
  `python/src/leanharbor_calculator/store.py`, `go/*/kernel/`, `go/calculator/store/`, and the SQL
  compiler and the token format in each shell) are committed and never edited.
  Run `make generate` after changing `lean/`.
- Authorization is the guard of `Leanharbor.Authz`: a kernel's `handle` decides a command with no
  authorization of its own, and the generated `transition` is `handle` behind `guardViewed` with
  the kernel's policy. The shells call `transition` only.
- When a function is added to a generated module, add a theorem about it and list it in the
  module's audit file (`audit/Audit/Calculator.lean`, `audit/Audit/Sql.lean`,
  `audit/Audit/Store.lean`, `audit/Audit/Token.lean`, `audit/Audit/Json.lean`,
  `audit/Audit/Notes*.lean`) in the same
  change.
  Theorems whose hypothesis fixes the result of the function (`transition a s c = .ok …`) cannot
  be run by leanassay; state the runnable form with `match` (`get_after_run`) and derive the
  other from it.
- The README states what is proved, what is checked and what is trusted. Keep its numbers equal
  to what `make check` and `make bench` print.

## Commands

All commands run inside `nix develop`.

- `make check`: `nix fmt -- --ci`, `lake -d lean build --wfail`, `lake -d audit build --wfail`,
  regeneration with `git diff --exit-code`, `cargo clippy -- -D warnings`, `cargo test`,
  `uv run pytest`, `go vet`, `go test -race`.
- `make generate`, `make format`, `make bench`.
- The README's Speed section shows rates (higher is better) with a chart for each table, and
  every cell has a value. `python3 tools/measure.py` runs every measurement and writes
  `docs/speed.json`; `python3 tools/speed-charts.py` draws `docs/speed-*.svg` and prints the
  tables to paste into the README. `bench/` holds the servers without a kernel that the HTTP
  measurement compares with; `make check` does not build them.
- The PostgreSQL tests (`rust/leanharbor-pg/tests/`, `rust/calculator/tests/postgres.rs` and
  `differential.rs`) start one server per test process with `leanharbor_pg::testing::cluster`
  (`initdb` and `pg_ctl` from the devShell, a Unix socket under `/tmp`) and give each test a
  database of its own; a test that cannot start the server fails. Queries of `pg_locks` and
  `pg_stat_activity` in a test filter on the test's database, since tests run in parallel on one
  server.
- The differential tests read the oracles' paths from `LEANHARBOR_CALCULATOR_ORACLE`,
  `LEANHARBOR_NOTES_ORACLE`, `LEANHARBOR_SQL_ORACLE`, `LEANHARBOR_TOKEN_ORACLE` and
  `LEANHARBOR_JSON_ORACLE`; the Makefile sets them. `tools/gen-commands.py` and
  `tools/gen-notes-commands.py` write the command lists.
  `testdata/sql-statements.txt` comes from `python3 tools/gen-statements.py 3000`,
  `testdata/token-cases.txt` from `python3 tools/gen-tokens.py 3000` and
  `testdata/json-cases.txt` from `python3 tools/gen-json.py 3000`; their line formats are
  described in `lean/SqlOracle.lean`, `lean/TokenOracle.lean` and `lean/JsonOracle.lean`.
- A spec in a proofs module calls no generated function, so that `#assay` does not break it along
  with the function (`kindOf` in `Leanharbor.Sql.Proofs` beside the generated `valKind`).
- The servers read `LEANHARBOR_SECRET` and `LEANHARBOR_LISTEN`; `LEANHARBOR_ISSUE=<org>:<user>`
  prints a one-day token and exits. The Rust calculator server stores the snapshots in PostgreSQL
  when `LEANHARBOR_DATABASE_URL` is set; with `LEANHARBOR_LOCKDOWN=<owner>:<engine role>` and an
  administrator's connection string it creates the tables for those roles and exits.

## Conventions

- Commit messages, comments and documents are in English.
- The leanfran compilers come from the flake input pinned to a release commit; the crate, the
  PyPI package and the Go module are pinned to the same version (`=0.11.0`, `==0.11.0`,
  `v0.11.0`).
